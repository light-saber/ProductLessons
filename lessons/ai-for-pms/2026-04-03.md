# RAG & Vector Databases: Giving AI a Memory It Can Search

**Topic:** RAG & Vector Databases  
**Date:** April 3, 2026

---

## 1. Technical Explanation

Retrieval-Augmented Generation (RAG) solves a fundamental LLM limitation: models only know what they were trained on. RAG works in three steps — **chunk** your documents into passages, **embed** each chunk into a high-dimensional vector (typically 768–3,072 dimensions) using an embedding model, then **store** those vectors in a vector database.

At query time, the user's question is also embedded, and the database performs approximate nearest-neighbor (ANN) search to find the most semantically similar chunks — typically in 2–12ms at p99 latency for million-scale datasets. Those chunks are injected into the LLM's prompt as context.

Key infrastructure choices: **Pinecone** (~4ms p50, fully managed), **Qdrant** (~2ms p50, best self-hosted performance), **pgvector** (good enough if you're already on Postgres). Leading embedding models like **Gemini Embedding 001** and **Cohere embed-v4** now support Matryoshka learning — you can truncate vectors to smaller dimensions with predictable quality loss, cutting storage costs significantly. Hybrid search (combining semantic vectors with keyword BM25) via Reciprocal Rank Fusion consistently outperforms either method alone.

---

## 2. Simple Explanation

Imagine you're a new PM joining Walmart. You have access to thousands of internal docs — PRDs, strategy decks, Slack threads. You can't read them all, but when someone asks a question, you need the right answer fast.

RAG is like giving the AI a brilliant research assistant. When a user asks something, the assistant speed-reads every relevant document, pulls the three best paragraphs, and hands them to the AI before it responds. The AI never memorizes your docs — it just reads the right ones at the right moment.

The "vector database" is the filing system that makes this instant lookup possible. Instead of matching keywords, it understands *meaning* — so searching "customer complaints about delivery" also finds documents about "shipping feedback" and "last-mile issues."

---

## 3. Real Example

Walmart's internal AI assistant helps associates answer product questions across millions of SKUs. Without RAG, an LLM would hallucinate product specs or prices. With RAG, each query triggers a retrieval against Walmart's product catalog stored as vectors — pulling live specs, pricing, and inventory data into the prompt.

The PM decision: rather than fine-tuning a model on product data (expensive, stale within days), the team chose RAG with nightly re-indexing. This meant product updates reflected in AI responses within 24 hours instead of weeks. They also chose hybrid search — semantic + keyword — because exact SKU numbers and brand names need keyword precision, while natural questions like "affordable waterproof camping tent" need semantic understanding.

---

## 4. Key Takeaways

- **RAG > fine-tuning** when your data changes frequently — it's cheaper, faster to update, and doesn't require retraining
- **Hybrid search** (semantic + keyword) almost always beats pure vector search in production
- **Embedding model choice matters** — Matryoshka-capable models let you trade storage cost for marginal quality loss at scale
- **Vector DB latency is rarely the bottleneck** — at 2–12ms, it's the LLM generation (500ms+) that dominates response time
- **RAG doesn't eliminate hallucinations** — it reduces them. You still need guardrails for when retrieval returns irrelevant results
