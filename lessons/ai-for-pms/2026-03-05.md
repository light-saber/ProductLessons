# AI for PMs: Latency, Throughput & Cost Optimization

**Date:** March 5, 2026  
**Topic:** Latency, Throughput & Cost Optimization

---

## Technical Explanation

Three metrics determine your AI product's economics: **Time to First Token (TTFT)**, **Time Per Output Token (TPOT)**, and **total cost per 1K tokens**.

**TTFT** measures milliseconds from API call to first response chunk. It's dominated by network overhead and model loading. **TPOT** measures generation speed once tokens start flowing—typically 20-100 tokens/second depending on model size and hardware. Total latency = TTFT + (TPOT × output length).

**Throughput** is requests or tokens processed per second across your fleet. Batching requests (sending multiple prompts together) dramatically improves throughput—often 5-10x—because GPU utilization increases. However, batching increases TTFT since the model waits for the full batch.

**Cost optimization levers:**
- **Model tiering**: GPT-5 mini at $0.25/1M input tokens vs GPT-5.2 at $1.75/1M vs GPT-5.2 pro at $21/1M
- **Prompt caching**: Reusing context across calls (up to 90% savings)
- **Batch API**: 50% discount for async processing (24-hour SLA)
- **Streaming**: Doesn't reduce actual latency but improves *perceived* latency by 40-60%

At Walmart scale, a 10% cost reduction on AI infrastructure could save millions annually.

## Simple Explanation

Think of AI responses like ordering food delivery.

**Latency** is the wait time: TTFT is how long until the delivery driver accepts your order (the "thinking" delay). TPOT is how fast they drive to your house once they've started. A long TTFT feels worse than a long TPOT—users hate staring at a loading spinner.

**Throughput** is the restaurant's capacity. One chef making one burger at a time = low throughput. Batching means the chef cooks 10 burgers simultaneously on a bigger grill. Each burger takes slightly longer, but total output per hour skyrockets.

**Cost optimization** is choosing the right restaurant for the job. A roadside dhaba for a quick snack (GPT-5 mini), a mid-range restaurant for family dinner (GPT-5.2), or a 5-star hotel for your anniversary (GPT-5.2 pro). Using the 5-star hotel for every meal bankrupts you.

The PM's job: match the customer's hunger level to the right kitchen, keep wait times acceptable, and watch the per-meal cost.

## Real Example: GitHub Copilot

GitHub Copilot generates code completions in real-time as developers type. Here's how PMs optimized the latency/cost tradeoff:

**The Challenge**: Developers type 60-100 WPM. If Copilot takes >300ms to suggest, the suggestion arrives *after* the developer has already moved on. But running GPT-4 for every keystroke would cost $50+ per developer per day.

**The PM Decision**: 
- Use a smaller, faster model (Codex) for inline completions—prioritizing TTFT <100ms
- Reserve the larger model (GPT-4 class) only when explicitly invoked (the chat sidebar)
- Implement aggressive prompt caching: the IDE context (open files, cursor position) is cached and reused across sequential keystrokes
- Enable streaming: show suggestions character-by-character rather than waiting for full completion

**Result**: Sub-100ms TTFT for 90% of completions at 1/10th the cost of using the largest model. The PM knew that *perceived* responsiveness matters more than absolute speed—and that developer productivity is worth paying for, but only up to a point.

## Key Takeaways

- **Measure TTFT and TPOT separately**—they have different fixes. TTFT improves with caching and model selection; TPOT improves with hardware and batching.
- **Perceived latency beats actual latency**—streaming responses make users feel the system is fast even when total time is unchanged.
- **Use the smallest model that works**—GPT-5 mini ($0.25/1M tokens) vs GPT-5.2 pro ($21/1M) is an 84x cost difference. Benchmark your use case on cheaper models first.
- **Batch for throughput, not latency**—batching improves efficiency but increases TTFT. Good for background jobs, terrible for real-time chat.
- **Prompt caching is free money**—if you're sending similar context repeatedly, you're burning cash. Implement caching layers aggressively.
