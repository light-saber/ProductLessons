# Agent Systems & Tool Use: When AI Stops Talking and Starts Doing

**Topic:** Agent Systems & Tool Use  
**Date:** 2026-03-24  
**Series:** AI for PMs

---

## 1. Technical Explanation

An **AI agent** is an LLM wrapped in a loop: perceive → reason → act → observe → repeat. Unlike a chatbot that generates text and stops, agents take *actions* — calling APIs, querying databases, writing files, browsing the web.

The core mechanism is **function calling** (aka tool use). You define tools as JSON schemas — name, description, parameters. The model decides *when* to invoke a tool and generates structured arguments. Your application executes the function and feeds results back into the conversation context for the next reasoning step.

**Key protocols emerging:**
- **Function Calling** (OpenAI, 2023): Model outputs structured JSON to invoke pre-defined functions.
- **MCP (Model Context Protocol)** (Anthropic, 2024; now Linux Foundation): An open standard — think "USB-C for AI tools." Client-server architecture using JSON-RPC 2.0. Agents discover and call tools dynamically without bespoke integrations.
- **A2A (Agent-to-Agent)** (Google, 2025): Lets agents from different vendors collaborate.

**Critical PM metrics:** tool-call accuracy (does the agent pick the right tool?), loop depth (how many steps before completion?), and failure recovery (what happens when a tool call errors?). By 2026, ~40% of enterprise apps embed agentic AI.

---

## 2. Simple Explanation

Think of a regular chatbot as a really smart person locked in a room with no phone, no computer — they can only *talk*. An agent is that same person, but now they have a toolbox: they can look things up, send emails, check inventory, place orders.

**Function calling** is essentially a menu card. You tell the AI: "Here are the tools you can use and what each one does." When someone asks a question, the AI reads the menu, picks the right tool, fills in the order form, and your system executes it. The result comes back, and the AI weaves it into a natural response.

MCP is the universal adapter — instead of building a custom plug for every tool, you build once to the standard and any AI can use it.

## 3. Real Example

Consider **Walmart's order support agent**. A customer asks: "Where's my order and can I change the delivery address?" A simple chatbot would say "contact support." An agentic system:

1. Calls `lookup_order(customer_id)` → gets tracking info
2. Calls `check_delivery_status(order_id)` → determines if rerouting is possible
3. Calls `update_address(order_id, new_address)` → makes the change
4. Responds naturally: "Your order ships tomorrow. I've updated the address."

The PM decision: define which tools the agent can access (read-only vs. write), set guardrails (max refund amount without human approval), and choose loop depth limits (max 5 tool calls per conversation to control cost and latency).

---

## 4. Key Takeaways

- **Agents = LLM + tool loop.** The model reasons; your system executes. The PM defines *which* tools and *what guardrails*.
- **Function calling accuracy is your #1 metric.** A wrong tool call is worse than no tool call — it erodes trust fast.
- **MCP is becoming the standard.** Betting on it reduces integration cost as your tool ecosystem grows.
- **Design for failure.** Tools will timeout, return errors, or hallucinate arguments. Build fallback paths and human escalation.
- **Loop depth = cost × latency.** Every tool call adds ~1-3 seconds and tokens. Cap it, measure it, optimize it.
