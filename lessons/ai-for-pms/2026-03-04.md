# Agent Systems & Tool Use: When AI Stops Just Talking

**Topic:** Agent Systems & Tool Use  
**Date:** March 4, 2026

## Technical Explanation

An **AI agent** is an LLM that can take actions — not just generate text. The key mechanism is **tool use** (also called function calling): you define tools (APIs, databases, code interpreters) as JSON schemas, and the model decides when to invoke them during a conversation.

The execution loop works like this: **User prompt → LLM reasons → emits tool call → your code executes the tool → result fed back → LLM continues reasoning.** This loop can repeat multiple times in a single turn, enabling multi-step workflows.

Key architectural decisions PMs must understand:

- **Tool definitions** are part of your prompt — each tool consumes tokens (~200-500 tokens per tool). Defining 50 tools eats your context window.
- **Reliability drops with complexity.** A single tool call succeeds ~95-98% of the time. Chain 5 steps and you're at ~77-90% reliability. This is the **compounding failure problem.**
- **Orchestration patterns** matter: single-agent (one LLM, many tools), multi-agent (specialized LLMs handing off), and human-in-the-loop (agent pauses for approval on risky actions).
- **Structured outputs** (strict schema validation) are now standard — they guarantee the model's tool call matches your expected format, eliminating parsing failures in production.

## Simple Explanation

Think of a regular chatbot as a person who can only talk on the phone — helpful, but limited. An **agent** is that same person, but now they have a desk with a computer, a calculator, and access to company systems.

When you ask "cancel my order," a chatbot says "here's how to cancel." An agent actually opens the order system, finds your order, checks the cancellation policy, and cancels it — then tells you it's done.

The PM's job is deciding **which tools to put on the desk** and **which actions need a human to approve** before the agent executes them. Too few tools = useless agent. Too many = confused agent that picks wrong ones.

## Real Example

GitHub Copilot evolved from a code-completion tool to an **agentic system** with Copilot Workspace. The PM decision: instead of just suggesting code, give the agent tools to read repositories, run tests, create PRs, and iterate on failures.

At Walmart scale, imagine an agent for merchant ops: a buyer asks "find me trending products under ₹500 in home décor with margin above 30%." Instead of generating a report template, the agent queries the catalog API, filters by margin thresholds, cross-references trend data, and returns an actionable shortlist. The PM decides: the agent can query and filter freely, but **reordering or price changes require human approval** — that's the human-in-the-loop pattern protecting against costly mistakes.

## Key Takeaways

- **Agents = LLMs + tools + execution loops.** The model reasons about *when* to use which tool — you define the toolbox
- **Reliability compounds negatively.** Every chained step multiplies failure risk — design for the fewest steps possible
- **Tool definitions eat tokens.** Be selective — 10 well-described tools beat 50 vague ones
- **Human-in-the-loop isn't optional** for high-stakes actions — it's a product design choice, not a limitation
- **Structured outputs eliminate parsing failures** — use strict schemas in production agent systems
